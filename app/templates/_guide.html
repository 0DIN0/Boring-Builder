How to use the builder

A quick tour, plus the habits that get good results out of a local model.

The 60-second version
  • 1. Pick a model. Under Builder models, create one sized to your hardware (check Settings → Hardware for what fits).
  • 2. Describe one subsystem. On the Build page, write a specific spec — one focused piece, not a whole app.
  • 3. Build. The model plans the files, writes each one, checks the Python compiles, and packages a zip.
  • 4. Download & run. Unzip, read the README, install requirements, run it.
Write specs that actually build

A local model follows direction far better than it invents it. The more concrete you are, the better the output.

  • Name the stack. "Flask + SQLAlchemy + MySQL", not "a backend".
  • List the pieces. Spell out the routes, the data model, and the rules: "User model with email + password hash; /signup, /login, /logout; secrets from .env".
  • Build one thing at a time. "User accounts" builds clean. "A whole social network" does not. Generate subsystems separately, then combine them.
  • Say where secrets go. Add "read all secrets from .env" and you'll get a .env.example instead of hard-coded keys.
  • Ask for tests. "Include a small pytest file" gives you a way to check it works.
Making a model — the simple version

You don't need to know anything about training. A "builder model" is just a base model plus a set of instructions (a Modelfile). It takes about a minute.

  • Go to Builder models → New builder model.
  • Give it a short name like web or api. It's saved as builder-web automatically.
  • Pick a base model that fits your hardware. On an 8 GB GPU, a 7B coder such as qwen2.5-coder:7b is a strong pick.
  • Edit the SYSTEM block if you want to change how it builds — the language, the framework, the house style. Everything else can stay as-is.
  • Click Create. A copy of the Modelfile is saved to modelfiles/builder/ so you can version it later.

Tip: keep a few specialised models rather than one do-everything model. A model told "you only write HTML, CSS and vanilla JavaScript" produces cleaner websites than a general one.

Which Ollama model should I use?

The Settings → Hardware panel detects your GPU and recommends models that fit. Rough rule of thumb:

≤ 4 GB VRAM3B coder models at context 4096. 6–8 GB VRAM7B coder models (≈5 GB) at context 4096–8192 — the sweet spot. 12 GB+ VRAM13B+ models, larger context windows. No GPURuns on CPU — slower, but 3–4B models are usable.

If a build fails with an out-of-memory or 500 error, the model is too big for your GPU: pick a smaller one or lower the context size, then try again.

Honest expectations

A 7B model on an 8 GB GPU writes solid single files and well-scoped subsystems, noticeably better than a 3B. It still won't one-shot a production app to the standard of a frontier hosted model. Keep scopes small, review what comes out, and treat it as a fast first draft. Every model call runs through one place in the code (ModelClient.chat), so you can point it at a hosted API later for frontier-quality output without changing anything else.
